## Context

用户需要一个视频理解服务，能够处理B站视频并生成文字摘要。当前没有现成的工具，需要从零构建。技术栈已确定：Python 3.14、uv包管理、Qwen3-ASR-1.7B本地部署、FastAPI服务化。

硬件环境：RTX 2060 Max-Q 6GB显存，独占使用，可支持Qwen3-ASR-1.7B模型（约3.5GB显存占用）。

## Goals / Non-Goals

**Goals:**
- 实现B站视频音频下载（支持BV号和URL）
- 集成Qwen3-ASR-1.7B进行本地语音识别
- 提供英文翻译为中文的功能
- 提供文字稿摘要功能
- 搭建RESTful API服务，支持本地其他服务器调用
- 完善的错误处理，任何环节失败都有明确错误信息返回

**Non-Goals:**
- 不支持实时流式处理，仅支持串行处理
- 不支持视频画面分析，仅处理音频
- 不支持批量并发处理
- 不提供用户界面，仅提供API

## Decisions

### 1. STT模型部署方式
**选择**: Transformers后端直接加载（非vLLM）
**理由**: 
- vLLM适合高并发生产环境，显存占用更高（4-5GB）
- Transformers更轻量，显存占用约3.5GB，6GB显存足够
- 串行处理场景不需要vLLM的continuous batching能力
- 单进程部署，无需管理多个服务

**备选方案**:
- vLLM独立进程：显存开销大，需要额外管理
- DashScope API：需要付费，用户暂无API Key

### 2. 音频下载方案
**选择**: yt-dlp
**理由**:
- 成熟稳定，支持B站
- 可配置仅下载音频流，提高效率
- 支持多种输出格式（选择wav便于STT处理）

### 3. 服务架构
**选择**: 单进程FastAPI + 内嵌STT模型
**理由**:
- 简化部署，无需管理多个进程
- 显存由应用统一管理
- 串行处理场景足够

**架构图**:
```
┌─────────────────────────────────────────────────────────┐
│                  FastAPI 服务 (单进程)                    │
│                                                         │
│   ┌─────────────────────────────────────────────────┐   │
│   │              Pipeline 编排                       │   │
│   │  download → stt → translate → summarize         │   │
│   └─────────────────────────────────────────────────┘   │
│                          │                              │
│         ┌────────────────┼────────────────┐             │
│         ▼                ▼                ▼             │
│   ┌──────────┐    ┌──────────┐    ┌──────────┐         │
│   │ yt-dlp   │    │ Qwen3-ASR│    │  LLM     │         │
│   │ (CPU)    │    │ (GPU 3.5G)│   │ (CPU/API)│         │
│   └──────────┘    └──────────┘    └──────────┘         │
└─────────────────────────────────────────────────────────┘
```

### 4. 错误处理策略
**选择**: 分层异常 + 统一响应格式
**理由**:
- 每个阶段定义专门的异常类（DownloadError, STTError等）
- 统一的错误响应格式，包含stage、code、message
- 调用方可根据错误码进行针对性处理

### 5. 翻译/摘要LLM后端
**选择**: 可配置支持多种后端（OpenAI API / 本地模型）
**理由**:
- 用户可能有OpenAI API Key
- 也支持本地部署的LLM
- 通过配置文件切换，灵活适配

### 6. 版本控制策略
**选择**: Git版本控制，每个功能完成后提交
**理由**:
- 保持清晰的提交历史，便于追踪开发进度
- 每个功能独立提交，便于回滚和代码审查
- 提交信息格式规范，提高可读性

**提交规范**:
- 提交信息格式：`<type>: <description>`
- type类型：
  - `feat`: 新功能
  - `fix`: 修复bug
  - `docs`: 文档更新
  - `refactor`: 代码重构
  - `test`: 测试相关
  - `chore`: 构建/工具相关
- 示例：`feat: 实现B站音频下载功能`

**提交时机**:
- 完成一个完整的功能模块后
- 通过相关测试后
- 代码审查通过后（如有）

## Risks / Trade-offs

### 风险1: GPU显存不足
**影响**: Qwen3-ASR-1.7B加载失败或推理OOM
**缓解措施**:
- 启动时检查显存，不足时给出明确错误
- 提供0.6B备选方案
- 推理完成后及时释放显存

### 风险2: B站反爬/需要登录
**影响**: 部分视频无法下载
**缓解措施**:
- 支持通过环境变量配置B站cookie
- 返回明确的AUTH_REQUIRED错误码
- 文档说明如何获取cookie

### 风险3: 音频质量差导致STT准确率低
**影响**: 文字稿质量差，后续摘要质量也受影响
**缓解措施**:
- 在API响应中返回音频时长，便于用户判断
- 考虑后续增加音频预处理（降噪等）

### 风险4: 翻译/摘要质量依赖LLM
**影响**: 如果LLM质量差，输出不可用
**缓解措施**:
- 支持多种LLM后端，用户可选择
- 提供原始文字稿，翻译和摘要是可选功能

### 权衡1: 串行处理 vs 并发处理
**选择**: 串行处理
**代价**: 无法同时处理多个视频
**收益**: 简化架构，避免资源竞争，6GB显存不适合并发

### 权衡2: 单进程 vs 微服务
**选择**: 单进程
**代价**: 模块间耦合度较高
**收益**: 部署简单，无进程间通信开销
